# Server Net

## 跨域问题和同源策略

1. **同源**，用于限制一个origin文档或者它加载的脚本如何能与另一个源的资源进行交互，能阻隔恶意文档，减少攻击。协议、域名/ip、端口都相同，即为同源。PS：同源策略下，服务器可以接收浏览器发来的请求，拦截的是服务器返回的数据。非同源不能相互操作DOM，不能互相读写Storage、Cookies等，不能通过AJAX的方式相互发送、接收数据；由于同源策略的限制，浏览器会阻止跨域请求，这包括Ajax请求、跨域资源嵌入（如< img >、< script >、< iframe >等）、跨域Cookie读取等操作。
2. **跨域**，由同源策略引发的开发问题，称为跨域问题。解决主流为CORS、代理两种。  
   - **CORS**：CORS是一套同于检验浏览器跨域请求的机制，基本理念是：只要服务器没有明确表示允许，则校验失败。需要后端解决。将请求分为简单请求和预检请求。不支持IE10以下
        - **简单请求**：请求方式为GET、HEAD、POST；Content-Type为text/plain，multipart/form-data/ ，application/x-www-form-urlencoded之一；头部字段不超出为Accept、Accept-Language、Content-Language；
        - **预检请求**：除简单请求外，浏览器会发一个预检请求检测请求是否通过。
3. **浏览器检测跨域原理**，浏览器检测到 ajax 请求的域与当前域不一致，会在请求头中增加 Origin 字段，然后检查服务端响应头 Access-Control-Allow-Origin，如果不存在或不匹配，则报跨域错误
4. **携带cookie跨域**，Access-Control-Allow-Origin 直接设置为通配符 * 时是无法通过浏览器的检查的，此时该响应头的值必须与发出请求的域完全匹配才行，另外，还需要设置 Access-Control-Allow-Credentials 响应头的值为 true，表示支持带 cookie 的跨域请求。
5. **反向代理**，服务器代理客户端的请求，原理：服务器与服务器之间没有跨域问题，在nginx中配置location路径。优点：1.负载均衡:将请求分发到多个后端服务器上；2.安全性，可以隐藏后端服务器的真实IP；缓存：可以缓存静态资源
6. **JSONP**，`<script> `标签的 src 属性却可以加载跨域的 JavaScript 脚本，JSONP 就是利用这一特性实现的。与普通的 Ajax 请求不同，在使用 JSONP 进行跨域请求时，服务器不再返回 JSON 格式的数据，而是将返回的数据包装成一个函数调用并返回给客户端，客户端再执行这个函数，来实现跨域。JSONP 的优点是兼容性好，在一些老旧的浏览器种也可以运行，但它的缺点也非常明显，那就是只能进行 GET 请求
7. **postMessage**:只支持GET
8. **domain**：cookie跨域，document.domain,可允许子域名页面跨域

## TCP三次握手和四次挥手

1. **第一次握手**，客户端向服务器发布请求连接报文，携带SYN(SYN标志用于请求建立连接)=1，初始序列号seq(用于标识每个TCP数据包的顺序)=x,客户端进入SYN-SEND状态；证明客户端的发送能力正常
2. **第二次握手**，服务器收到请求报文后，如果同意连接，则会向客户端发出确定报文。确认报文中应该包含ACK(确认标志位，对已接收的数据包进行确认)=1,SYN=1,ack(TCP对上一次seq序号做出的确认号)=x+1，同时自己初始化一个序列号seq=y，服务器进入SYN-RCVD状态；证明服务器端的接收能力、发送能力正常
3. **第三次握手**，客户端收到确认后，向服务器给出确认。确认报文ACK=1，ack=y+1，自己的序列号seq=x+1,此时进入ESTABLISHED已建立连接状态,证明客户端的接收能力正常
:::tip 为什么不使用二次握手
如果client的一个请求连接报文在网络中长时间滞留了,以致延误到连接释放以后的某个时间才到达server,但server收到此失效的连接请求报文段后，就误认为是client再次发出的一个新的连接请求,并一直等待client发来数据,但是client并没有请求连接,这样server的资源就被浪费了
:::
挥手过程可以是client发起,也可以是server发起,假设为client发起:
1. **第一次挥手**:client发布连接释放报文,停止发送数据,携带FIN=1,序列号seq=u(等于前面已经传送过来的最后一个字节序号+1),此时客户端进入FIN-WAIT-1状态
2. **第二次挥手**:server收到报文后,发出确认报文,ACK=1,ack=u+1,此时服务端进入CLOSE-WAIT状态
3. **第三次挥手**:client收到服务器的确认请求后,客户端进入FIN-WAIT-2,继续等待服务器连接释放报文,服务器将最后的数据发送完毕后,向客户端发送FIN=1,ACK=1,seq=w,ack=u+1,此时服务器进入LAST-ACK(最后确认)状态
4. **第四次挥手**:client收到服务器连接释放报文后,发布确认.ACK=1,ack=w+1,seq=u+1,此时客户端进入TIME-WAIT状态,但此时TCP连接还未终止,必须要经过2MSL后,客户端才会进入CLOSED关闭状态,服务器收到确认报文后,也进入CLOSED状态
5. 客户端等待2MSL(报文最大生存时间):假设最后的ACK丢失，server将重发FIN，client必须维护TCP状态信息以便可以重发最后的ACK
:::tip 为什么是四次挥手
建立连接时因为当Server端收到Client端的SYN连接请求报文后，可以直接发送SYN+ACK报文。其中ACK报文是用来应答的，SYN报文是用来同步的。所以建立连接只需要三次握手。而挥手的时候,Client端发出FIN报文段时，只是表示Client端告诉Server端数据已经发送完毕了,但是Server端还是可以发送数据到Client端的.当Server端也发送了FIN报文段时，这个时候就表示Server端也没有数据要发送了.
:::

## CDN

CDN是内容分发网络,构建在现有网络基础之上的智能虚拟网络，通过部署在各地的边缘服务器，通过中心平台的负载均衡、内容分发、调度等功能模块，使用户能够就近获取所需内容，从而降低网络拥塞，提高用户访问响应速度和命中率
应用CDN后，DNS解析不再返回IP地址,而是返回一个CNAME(别名记录),指向了CDN的全局负载均衡,负载均衡系统:本地DNS会向负载均衡系统发送请求，然后进入CDN的全局负载均衡系统进行智能调度

CDN查询过程:
1. 查看用户IP地址,查表得知地理位置,找到相对最近的边缘节点;
2. 查看用户所在运营商网络,找到相同的网络边缘节点;
3. 检查边缘节点的负载情况,找负载较轻的节点;
4. 其他因素,如节点的服务能力,带宽,响应时间等

缓存代理:
1. 缓存系统会有选择地缓存那些最常用的资源,有两个衡量CDN服务质量的指标:命中率(命中次数/所有访问次数)&回源率(回源次数/所有访问次数)
2. 缓存有一级缓存,二级缓存,回源的时候二级找一级,一级找源站,提高效率.

## Cookie怎么防止XSS\CSRF攻击

1. 使用HttpOnly属性,HttpOnly 可以防止客户端 JavaScript 访问该 Cookie
```ts
Set-Cookie: myCookie=value; HttpOnly
```
2. 使用 Secure 属性,设置 Secure 属性会导致 Cookie 仅在 HTTPS 连接中被发送
```ts
Set-Cookie: myCookie=value; Secure
```
3. 使用 SameSite 属性,SameSite 属性可以防止 CSRF（跨站请求伪造）攻击。它可以设置为 Strict、Lax 或 None。
   1. SameSite=Strict，Cookie 只会在同站请求中被发送。当用户从其他网站点击链接跳转到当前网站时，浏览器不会携带 Set-Cookie 设置的 Cookie。这种设置提供了最高的安全性，但也可能影响用户体验，因为在完全不同的站点跳转时，用户无法保持登录状态。
   2. SameSite=Lax,Cookie 会在同站请求中被发送，并且在某些安全的跨站请求中也会被发送，比如用户从其他网站进行 GET 请求时。这意味着用户可以通过链接从其他域转到该站点时，Cookie 会被发送，但表单提交等其他方式不会发送 Cookie.这种设置在安全性和用户体验之间取得了平衡，是许多应用的推荐设置
   3. SameSite=None,Cookie 会在所有请求中发送，包括跨站请求。为了确保安全性，您必须同时设置 Secure 属性，这意味着 Cookie 只能通过 HTTPS 发送.这种设置适用于需要在不同域之间共享 Cookie 的情况，但不推荐在默认情况下使用，因为它可能使应用易受 CSRF 攻击
```ts
Set-Cookie: myCookie=value; SameSite=Lax
```
4. 合理设置 Cookie 的过期时间,确保 Cookie 有合理的过期时间，防止长期存储过期的敏感信息。
```ts
Set-Cookie: myCookie=value; Expires=Wed, 09 Jun 2021 10:18:14 GMT
```
5. CSP,通过设置 CSP，可以限制能够在页面上运行的 JavaScript 来源
6. 输入验证和过滤,确保对用户输入进行严格的验证和过滤，防止恶意脚本注入
